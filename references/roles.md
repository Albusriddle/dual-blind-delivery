# 角色边界

> 本文件规定"谁能看什么、谁能写什么、谁对什么负责"。任何冲突以本文件为准。

---

## 1. Lead（唯一决策人）

**职责**
- 写合同 `contract/SPEC.md` 与门禁配置；写／维护 `validate.mjs`
- 派工：给两个生产者**逐字相同**的提示词；给复核员"先 KEY 后复核"的两阶段指令
- 合并 A/B，逐条关闭 blocker，记录 `MERGE_NOTES.md`
- 维护 `ROUNDS.md`（只追加）
- 唯一有权宣布"进入下一阶段"

**禁止**
- 替生产者写内容（Lead 的答案草稿会污染双盲）
- 在门禁为红时宣布前进
- 自己验证自己提出的问题已关闭（要由提出方复验）

**产物**：`contract/*`、`final/*`、`MERGE_NOTES.md`、`ROUNDS.md`、`MANIFEST.sha256`

---

## 2. 生产者（A / B）

**职责**
- 只依据「源材料 + 合同」独立完成**完整可交付**的版本
- 自建构建脚本，保证产物可一键重跑
- 跑通 `validate.mjs`
- 写 `NOTES.md`：自检证据（命令 + 输出）、**主动自陈已知不足 ≥1 条**、对源材料的修正记录

**禁止**
- 读另一侧目录（`b/` 之于 A、`a/` 之于 B）
- 读 `audit/`（复核员的基线）
- 修改源材料、修改 `contract/`
- 交付半成品（"先交一部分让复核看看"= 浪费复核预算）

**隔离的工程实现**
- 不同目录、不同构建命令
- 提示词逐字相同，只替换目录名与任务 id
- 如需共享资料，**只能**共享 `contract/` 与源材料的只读副本

---

## 3. 复核员（第三人）

**职责**
- **阶段一（P2）**：不看 A/B，独立从源材料建立 `audit/KEY.md`
- **阶段二（P3）**：逐条比对 A、B 与 KEY，出 `REVIEW.md` + `ERRATA.json`
- **阶段三（P5）**：复跑断言验证修复，出 `FINAL_REVIEW.md`（含 Δ 复核）

**禁止**
- 在写 KEY 期间打开 `a/`、`b/`（这是"第三人"有效性的全部前提）
- 用"感觉不错"代替判决：每一行必须有证据
- 修改产物（复核员只读；发现问题写进报告，由 Lead/生产者改）

**独立性约定（三选一，写进报告开头）**
1. 时间戳证明：KEY 的 mtime 早于首次读取 A/B
2. 提交顺序证明：KEY 先 commit，再开放目录
3. 声明 + 抽查：声明未读，并由 Lead 抽 3 条 KEY 内容与 A/B 措辞比对（无雷同）

**工程化落地（推荐）**：Lead 在 G1 绿之后执行
`mkdir -p _sealed && mv a b _sealed/`，KEY 落盘并记录哈希后再 `mv` 回来；
`_sealed/SEALED.mtime` 的哈希写入 ROUNDS.md，作为"先 KEY 后产物"的证据。
做不到移目录时，至少保证发给复核员的第一条消息里不出现 `a/`、`b/` 的路径。

---

## 4. 二审人（第四人，或复核员新轮）

**职责**
- 只做两件事：**复跑断言** + **Δ 复核**
- 结论三选一：`通过` / `有条件通过（列出非阻塞项）` / `打回（列 blocker）`

**禁止**
- 复述一审结论
- 接受"报告说已修"
- 对审核后改动"顺手看看"而不逐项验证

> 二审人与一审人相同是允许的（大任务建议不同人）。但必须是一次**新鲜的、独立的**执行轮次，不能沿用一审时的中间态。

---

## 5. 沟通协议

| 谁 → 谁 | 内容 | 形式 |
|---|---|---|
| Lead → 生产者 | 合同、门禁命令、交付清单 | 提示词（逐字相同） |
| 生产者 → Lead | 自检输出 + 已知不足（≤10 行） | 一条汇报 |
| Lead → 复核员 | 阶段一：只给源材料 + 合同；阶段二：再开放 `a/`、`b/` | 两条消息（时序即隔离） |
| 复核员 → Lead | blocker 优先、结构化（表格/JSON） | 报告文件 + ≤10 行摘要 |
| Lead → 二审人 | 交付字节哈希 + 上次通过的版本哈希 | 一条消息（Δ 的边界） |

**反模式**：Lead 把"我觉得这里应该改"直接告诉生产者 → 双盲被污染，差异不再可信。要改，走复核员的正式结论。
